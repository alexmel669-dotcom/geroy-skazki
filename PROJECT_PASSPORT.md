### Продуктовое обещание

**Для ребёнка:** Люцик — понятный и доброжелательный персонаж, с которым можно разговаривать, играть, придумывать сказки и делиться переживаниями.  
**Для родителя:** безопасная цифровая среда, прозрачные настройки, сведения об активности и возможность поддерживать разговор с ребёнком.

**Ограничение:** продукт не должен обещать диагностику, лечение или гарантированное устранение психологических проблем. ИИ не заменяет родителей, врача или квалифицированного специалиста.

## 2. Первоначальная концепция и границы изменений

### Продуктовый «скелет», предлагаемый на утверждение
1. Люцик — центральный узнаваемый персонаж; голосовой интерфейс доступен детям, которые ещё не читают.
2. Основной сценарий — общение, сказки и игры, а не бесконечный просмотр контента.
3. Доброжелательная персонализация с учётом имени, возраста и разрешённого контекста.
4. Тамагочи-механика: дом Люцика, забота, прогресс, награды.
5. Отдельный защищённый родительский кабинет с понятными настройками и отчётами.
6. Индивидуальная изоляция каждой семьи и каждого ребёнка; информация используется только по разрешённым целям.
7. Доступные психологам функции отделены от данных семей и ограничены согласиями/правами.
8. Приложение должно оставаться простым, ориентированным на русскоязычных детей; допустимы PWA и магазинные сборки.
9. Все существенно новые расходы, модели ИИ, сервисы, изменения памяти и обработки данных требуют решения владельца.
10. MVP сначала, дополнительные WOW-функции — только после проверки основного пути и безопасности.

### Отдельные задумки, не подтверждённые как обязательная реализация
- Полностью непрерывный голосовой диалог с прерыванием ответа (barge-in) без нажатия микрофона.
- Аватар ребёнка по фотографии в стиле 3D/Pixar, с удалением исходного фото.
- Генерация сказок голосом родителя.
- Расширенный кабинет психолога, углублённые метрики, спецсценарии для особенностей развития.
- Подписка и монетизация на сайте; магазинная версия без оплаты.

Эти предложения **не считаются уже работающими**. Владельцу нужно утвердить приоритет и объём каждой функции.

## 4. «Мозг» Люцика — пользовательский ИИ

### Назначение
Подсистема обеспечивает ответы ребёнку, персонализацию, сказки, запоминание разрешённого контекста, выбор роли/тона, голосовой ввод-вывод, безопасность речи и контроль затрат.

### Предполагаемая цепочка
```
Речь/текст ребёнка
  ↓
Распознавание речи: браузер / STT API (по доступности)
  ↓
Авторизация, ограничения, данные конкретного ребёнка
  ↓
Контекст и разрешённая память
  ↓
Системная инструкция и выбор сценария (чат/сказка)
  ↓
Серверный generate → внешняя ИИ-модель
  ↓
Фильтрация/форматирование результата
  ↓
TTS и анимация Люцика
  ↓
Сохранение разрешённых данных и обновление отчётов
```
Это **логическая схема для проверки**, а не доказательство полного прохождения всех этапов в production.

### Что видно в main
- `generate.js`: шаблоны подсказок для разных персонажей, возраста, грамматических правил, сказок и чата; используется Redis и ограничение запросов.
- `ai.js`: переключение персонажей, история и лимиты сообщений; есть использование `localStorage`.
- `context.js`: время суток, день недели, приветствие, контекст для ответа.
- `speech-to-text.js` и `tts.js`: серверная интеграция Yandex SpeechKit.
- `users.js`: Redis через `@upstash/redis`, в старой версии данные и диалоги адресуются ключами, зависящими от email.
- Выбор и актуальность конкретной модели DeepSeek, фактические лимиты, политика долговременной памяти и механизм «прерывания Люцика» требуют отдельного аудита полного потока и окружения.

### Обязательные правила
1. Уникальная идентичность семейного аккаунта не должна зависеть только от email.
2. Сведения одного ребёнка нельзя выдавать другому, даже внутри одной семьи, если доступ не разрешён.
3. Удаление аккаунта должно учитывать все связанные записи и сессии.
4. Контекст и промпты не должны раскрывать чужие данные или отправлять лишнюю персональную информацию внешним провайдерам.
5. ИИ не ставит диагноз, не заменяет живого специалиста и избегает внушения ребёнку зависимости от ИИ.
6. Изменение провайдера, модели, памяти, передачи данных и стоимости — только после решения владельца.
7. Должны измеряться latency, ошибки STT/TTS, стоимость запроса, доля безопасных ответов, корректность семейной изоляции.

В PR №5 дополнительно подготовлены `AGENTS.md`, `.agents/skills/*` и `.github/workflows/release-checks.yml`; это не означает, что они находятся в `main`.

### Runtime и зависимости
- Язык: JavaScript ES modules, некоторые TypeScript-файлы и `tsc --noEmit`.
- Web/API: Node.js HTTP-сервер, API handlers, публичная статика.
- Хранилище в `main`: `@upstash/redis` с переменными `KV_REST_API_URL`, `KV_REST_API_TOKEN`.
- JWT: библиотека `jsonwebtoken`.
- Тесты: Vitest; проверки синтаксиса и типов.
- Speech: Yandex SpeechKit через API handlers.
- AI: серверный API `/api/generate` и внешняя модель; действующая конфигурация провайдера NOT_VERIFIED.
- PWA: service worker, web manifest.
- Деплой: фактические файлы на VPS, конфигурация PM2/Nginx и среда ENV **не проверены**. В `server.js` до сих пор имеются совместимые ветки Vercel/Railway/Render — их присутствие в коде не подтверждает использование этих платформ сейчас.

### Данные и хранение
- Redis-профили и история; индексы и ключи старого формата в `main`.
- Browser `localStorage` для части истории/состояния; определить все ключи, сроки, синхронизацию и удаление.
- Отдельно проверить данные согласий, психологов, чатов, статистики, жалоб, PIN, токенов детей, резервных копий, журналов.
- Никаких реальных данных детей в Git, задачах Codex, CI или тестовых стендах.

### Подтверждённый дефект в публичном `main`
- `api/_lib/users.js`: `deleteUser(email)` удаляет `geroy:user:<email>` и запись из `geroy:users`, но не удаляет `geroy:dialogs:<email>`.
- `api/_handlers/delete-account.js`: после `deleteUser(email)` возвращает пользователю утверждение «Все персональные данные стёрты».
- `api/_middleware/auth.js`: `verifyAuth` проверяет JWT криптографически, но сама функция не проверяет, существует ли аккаунт и не отозван ли токен. Вызовы должны проверяться в контексте маршрутов — риск особенно важен при удалении и повторной регистрации.
- Эти выводы относятся к прочитанным файлам **GitHub `main`**, а не к локальному исправлению Issue №6 и не к действующему VPS.

## 8. Пользовательские сценарии и критерии приёмки

**Родитель:** открыть лендинг → понять назначение → зарегистрироваться → дать нужные согласия → создать ребёнка → настроить безопасный доступ → открыть кабинет → просмотреть отчёт → удалить аккаунт и связанные данные по проверяемой политике.

**Психолог:** зарегистрироваться/подать заявку → получить ограничённый доступ только после одобрения и согласий → использовать доступные данные по своей роли → лишиться доступа при отзыве.  
**Владелец проекта:** открыть Owner Hub → увидеть текущие факты и SHA → оценить работу агентов и изменение «было/стало» → протестировать изолированный кандидат → одобрить/отклонить существенные изменения → разрешить выпуск после QA.

Для каждого сценария перед выпуском требуются: положительный путь, отказ доступа, ошибочные вводы, обновление PWA, работа без сети (по заявленным возможностям), отзыв сессии и доказательство разделения аккаунтов.

## 10. Управление разработкой и агентами

### Роли
- Владелец: утверждает продукт, бюджет, архитектурные изменения и релиз.
- Главный координатор: формирует задачи, сверяет отчёты и риски, не утверждает за владельца.
- Codex Developer: реализует задачу в отдельном worktree, запускает проверки.
- Independent QA: независимо проверяет точный SHA и критерии.
- SecurityAgent: регрессии прав, JWT, данных, секретов.
- SyncAgent: обнаружение отклонений файлов и версий, без автосинхронизации production.
- ContentAgent: анализ публичных формулировок.
- CostObserver: подписки/лимиты/стоимость, без права покупки.
- Owner Hub: интерфейс наблюдения и тестирования; не источник достоверности сам по себе.

### Контракт задачи
`ID задачи → утверждённая версия плана → исходный SHA → разрешённые файлы → критерии приёмки → оценка рисков/затрат → код и тесты → QA SHA → решение владельца → публикация/закрытие → дневной отчёт`.

### Контроль изменений
- Обычные изменения внутри задачи выполняются автономно.
- Изменение концепции, памяти ИИ, передачи детских данных, модели, существенных функций, бюджета или внешних сервисов → APPROVAL_REQUIRED.
- Каждое предложение должно объяснять человеческим языком: «что сейчас», «что лучше», «чем доказано», «цена», «риск», «что если не менять».
- Молчание владельца не означает согласия. Агент не может сам вписать `APPROVED` как разрешение.
- Контроль на двух уровнях: дисциплина агента + внешняя GitHub/CI-проверка на доверенной базе.
- Тестовая версия должна работать только с синтетическими данными, не с production Redis.

## 14. Принципы доказательств и ежедневной актуализации

- Не изменять утверждённый продуктовый план незаметно. Новая версия только через заявку и решение владельца.
- Ежедневный статус формируется из проверяемых источников; сохранять даты, окружения, SHA, результаты, пропуски и причины.
- Проверки с неизвестным результатом не превращаются в PASS от заполнения `verified: true`.
- Все существенные результаты работы агента сопровождаются ссылкой на diff/коммит и описание на человеческом языке.
- `main`, production VPS, PR №4/5, локальные worktree и тестовый стенд — отдельные сущности; не смешивать.
- При отсутствии доступа к VPS или Windows отражать NOT_VERIFIED.
- Релиз остаётся HOLD, пока P0 и обязательные release-gates не закрыты.
